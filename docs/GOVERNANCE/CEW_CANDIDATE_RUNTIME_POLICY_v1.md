# CEW Candidate Runtime Policy v1

Status: REQUIRED DELIVERY / HUMAN-ACCEPTANCE INFRASTRUCTURE  
Date: 2026-08-28  
Machine contract: `automation/CEW_CANDIDATE_RUNTIME_POLICY_v1.json`

## 1. Purpose

CEW requires a stable runtime for Human Acceptance candidates that is independent from the frequency of AI-assisted development commits.

The runtime is **not** a source of product or engineering authority. Its purpose is to expose one immutable, already-validated candidate to a participant/reviewer under controlled conditions.

The governing lifecycle is:

`WORKING COMMITS -> GITHUB GATES -> IMMUTABLE CANDIDATE -> CANDIDATE RUNTIME -> HVA -> PROMOTION DECISION`

and never:

`EVERY COMMIT -> HOSTING DEPLOYMENT`.

## 2. Provider model

### Primary — Render

Render is the primary Candidate/HVA runtime for the current development phase.

Service:

`cew-hva-candidate`

Declared infrastructure:

`render.yaml`

Configuration:

- Python web service;
- Free instance;
- Frankfurt region;
- `autoDeployTrigger: off`;
- exact-commit/manual deployment;
- `uvicorn app:app --host 0.0.0.0 --port $PORT`;
- health/readiness path `/readyz`.

Render is chosen for this phase because it runs the existing FastAPI application directly and does not require a framework/runtime migration merely to obtain a Human Acceptance environment.

### Fallback — Vercel

Vercel remains a controlled Preview fallback under:

`automation/CEW_VERCEL_DEPLOY_POLICY_v1.json`

Working commits remain excluded from automatic Preview creation. Provider availability must not alter candidate identity or acceptance semantics.

## 3. Exact-revision rule

A Candidate/HVA deployment is valid only when the runtime exposes the exact immutable SHA that passed the declared automated gates.

On Render, `RENDER_GIT_COMMIT` is used as runtime identity.

`/readyz` exposes this value as `runtime_revision`.

Before HVA:

`runtime_revision == accepted candidate SHA`

must be true.

A deployment of a different SHA cannot borrow automated or human evidence from the accepted candidate.

## 4. Managed-runtime fail-closed behavior

Render and Vercel are treated as managed runtimes.

On managed runtimes:

- `CEW_AUTH_DISABLED_FOR_TEST=1` cannot disable authentication;
- session cookies remain secure;
- local filesystem receipt persistence is not accepted;
- a persistent audit backend is required;
- missing auth or persistent audit configuration causes `/readyz` to return HTTP 503;
- `canonical_write_authorized` remains `false`.

This prevents a technically running but incorrectly configured service from being treated as HVA-ready.

## 5. Readiness contract

Render's service health check uses:

`GET /readyz`

A valid Candidate/HVA runtime returns HTTP 200 with:

- `status = READY`;
- `runtime_provider = RENDER`;
- `runtime_role = CANDIDATE_HVA`;
- `runtime_revision = exact candidate SHA`;
- `auth_configured = true`;
- persistent audit backend in the allowed set;
- `canonical_write_authorized = false`.

If any required runtime configuration is missing, `/readyz` returns HTTP 503.

`/healthz` remains a diagnostic endpoint and does not replace `/readyz` as the acceptance-runtime readiness signal.

## 6. Persistent audit boundary

Render Free has an ephemeral filesystem. Therefore CEW Human Acceptance receipts must not rely on local runtime files.

The preferred current backend is:

`NEON_APPEND_ONLY`

configured through:

`CEW_AUDIT_NEON_DATABASE_URL`

The existing allowed persistent alternatives remain:

- `SUPABASE_APPEND_ONLY`;
- `NETLIFY_AUDIT_HTTPS`.

No database credential is committed to the repository.

## 7. Render environment contract

The Blueprint declares:

- `CEW_RUNTIME_ROLE=CANDIDATE_HVA`;
- `CEW_AUTH_DISABLED_FOR_TEST=0`;
- `CEW_SESSION_SECRET` generated by Render;
- `CEW_ACCESS_PASSWORD` supplied externally;
- `CEW_AUDIT_NEON_DATABASE_URL` supplied externally.

The two externally supplied values are secrets and remain outside Git.

## 8. Free-tier operating rule

A Free Render web service may spin down during inactivity. This is acceptable for the current Human Acceptance phase but must not be confused with Production-grade availability.

Before a moderated or controlled HVA session:

1. request `/readyz`;
2. allow the free service to wake if necessary;
3. confirm HTTP 200 and exact runtime SHA;
4. only then begin participant observation.

The wake-up request is operational preparation, not acceptance evidence.

## 9. Candidate lifecycle

A typical iteration becomes:

1. agents/developers produce any number of working commits;
2. no Candidate/HVA hosting deployment is required;
3. one SHA is frozen as candidate;
4. all declared GitHub gates run on that SHA;
5. the candidate is deployed to Render using **Deploy a specific commit**;
6. `/readyz` proves configuration and SHA identity;
7. participant/reviewer HVA runs;
8. failure returns to development and creates a new candidate SHA;
9. success can proceed to the remaining promotion gates.

## 11. Production boundary

Render Free Candidate/HVA runtime is not CEW Production.

A successful Render HVA does not imply:

- CEW B1 promotion;
- `CEW_PROMOTED_BASELINE`;
- Production deployment;
- canonical engineering write;
- engineering approval.

Production remains a downstream, separately governed release state.

## 12. External one-time setup

Repository configuration is complete when this policy is merged. One external binding remains necessary because no Render account connector is available in the current tool environment:

1. create/connect one Render Blueprint instance from `render.yaml`;
2. enter `CEW_ACCESS_PASSWORD`;
3. enter `CEW_AUDIT_NEON_DATABASE_URL`;
4. let Render generate `CEW_SESSION_SECRET`;
5. verify `/readyz`.

After that one-time binding, ordinary development requires no hosting action until a green immutable candidate exists.
